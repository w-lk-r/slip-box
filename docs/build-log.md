## Week 3 — FastAPI Backend Planning (Aug 21, 2026)

- Researched how to wire a FastAPI backend to the deployed AgentCore Runtime agent (invoking `bedrock-agentcore`'s `invoke_agent_runtime` via boto3, `runtimeSessionId` must be 33–256 chars — bare `uuid4()` at 32 chars is rejected, session IDs generated as `f"session-{uuid.uuid4()}"`).
- **Considered and rejected `agentcore add gateway`/BYO-agent as the API's front door.** AWS docs confirm AgentCore Gateway hard-restricts to GET/POST/DELETE only (no PATCH/PUT — blocks a plain edge-edit endpoint) and has no workable browser-auth story without standing up Cognito/OIDC. Confirmed this isn't a scoring risk either way — the hackathon rules state AgentCore usage strengthens Technical Implementation but "it's not required," and the agent itself is already correctly deployed on AgentCore Runtime regardless of what fronts the web API.
- **Confirmed API Gateway's Lambda-proxy integration has a hard, un-raisable ~29s timeout**, and `/ingest`'s multi-tool-call agent loop can realistically exceed it. Verified this is a real, AWS-documented limitation by reading AWS's own `aws-samples/sample-expose-agentcore-via-api-gateway` repo directly — their proxy Lambda timeout is set to exactly 30s to match, and their README names the limitation outright, pointing to AgentCore Gateway (not Function URLs) as their fix.
- **Decision: keep API Gateway exactly as originally scoped, make `/ingest` asynchronous instead.** A lightweight `ApiFunction` (FastAPI + Mangum) validates input and asynchronously invokes a second `WorkerFunction` (not fronted by API Gateway, so free of its timeout) that does the actual blocking `invoke_agent_runtime` call; the frontend polls `GET /items` for the result. Sidesteps the timeout entirely without deviating from AgentCore, without AgentCore Gateway's constraints, and without needing Lambda Function URLs or response streaming. REST API (not HTTP API) chosen specifically for native API Key + Usage Plan support, which satisfies review-todo #11's auth+rate-limiting requirement through infra config rather than hand-rolled app code.
- Full plan: two Lambda functions (`ApiFunction`, `WorkerFunction`) in a new `agentcore/cdk/lib/api-stack.ts` (same hand-rolled Foundation Stack pattern as `app-stack.ts`), new `app/api/` Python package (own `pyproject.toml`, Lambda-packaged via `uv pip install --target`, no Docker). Endpoints: async `POST /ingest`, `GET /items`, `GET /graph`, `PATCH`/`DELETE /edges/{from_id}/{edge_id}` (composite path — `slip-box-edges`' key schema is PK `from_id` + SK `edge_id`, no GSI for point-addressing by `edge_id` alone).
- Bedrock Guardrails deferred (would touch `MyAgent`'s model invocation, not this new stack; needs real threshold-tuning to be worth building) — plug-in point documented as `app/MyAgent/model/load.py`'s `load_model()`, for whenever `MyAgent` is next touched.

- Built the FastAPI backend per the plan: `agentcore/cdk/lib/api-stack.ts` (`ApiFunction` + `WorkerFunction`, REST API Gateway with native API Key + Usage Plan), `app/api/` package (`main.py`/`worker.py`/`routers/{ingest,items,graph,edges}.py`/`linkgen.py`/`models.py`/`clients.py`/`serialize.py`, `build.sh` for `uv`-based Lambda packaging targeting `aarch64-manylinux2014` to match ARM_64).
- Verified locally before any deploy: `tsc` compiles clean; `cdk synth` (via the real CLI at `node_modules/.bin/cdk` — `npx cdk` gets shadowed by this project's own `package.json` `bin.cdk` entry pointing at the app itself, worth remembering next time) produces exactly the expected resources — both Lambdas with correct handler/runtime/arch/timeout/env vars, precisely-scoped IAM policies (worker only gets `bedrock-agentcore:InvokeAgentRuntime`; the agent's own writes stay on the agent's IAM role), `ApiKeyRequired: true` on both proxy methods, usage plan throttle (5 rps/10 burst) and quota (2000/day) correctly attached to the stage.
- Verified the Python side against real AWS (not mocked): `POST /ingest` validation (422 on empty body, on both `text`+`url` together, on `research: true` → 501); `GET /items` and `GET /graph` return real data with `Decimal` confidence values correctly serialized as floats; `PATCH`/`DELETE /edges/{from_id}/{edge_id}` tested end-to-end on a throwaway edge — type/confidence update, history append, frontmatter regeneration on type change, and post-delete frontmatter cleanup all confirmed against the real S3 object.
- **Deployed** (`npm run deploy:api`) and found two real bugs the local/pre-deploy testing couldn't catch, both fixed and redeployed:
  - `WorkerFunction` crashed on cold start with `KeyError: 'S3_BUCKET'` — `worker.py` imported the shared `clients.py`, which unconditionally requires `S3_BUCKET`/`ITEMS_TABLE`/`EDGES_TABLE` at module load even though the worker never uses them (least-privilege design only gives it `AGENT_RUNTIME_ARN`). Fixed by giving `worker.py` its own minimal inline client setup instead of sharing the full module.
  - `bedrock-agentcore:InvokeAgentRuntime` 403'd against the deployed IAM policy even though the policy's `Resource` matched the runtime ARN exactly — the API actually operates on a `.../runtime-endpoint/DEFAULT` sub-resource (same pattern as an S3 bucket vs. its objects), so the policy needed `[agentRuntimeArn, \`${agentRuntimeArn}/*\`]`. This only surfaced once the Lambda's own narrowly-scoped role made the call — all earlier testing used broad local credentials that didn't exercise the resource-level restriction.
  - Both bugs found by actually invoking through the deployed stack (CloudWatch logs on `WorkerFunction`), not by code review — real infra behavior (env var propagation, IAM resource ARN shapes) that can't be verified any other way.
- Full round trip verified against the live deployed stack: `POST /ingest` → 202 with session ID (instant, confirming the async handoff isn't blocking) → agent completed in ~36s (comfortably past what API Gateway's 29s timeout would have allowed, validating the whole async design) → note + 3 correctly-typed edges (RELATED_TO/SUPPORTS/EXTENDS) visible via `/items` and `/graph` → `PATCH`/`DELETE` on a throwaway edge through the live API, frontmatter regenerated correctly on the real S3 object. Also confirmed the auth guardrail: 403 with no/wrong API key, 200 with the correct one.
- `review-todo.md` #11 marked RESOLVED — see there for detail.

- Fixed `update_summary`'s clobber bug (review-todo #9): it now reuses `write_edge`'s `_parse_frontmatter`/`_render_frontmatter` helpers to regenerate frontmatter from S3, only touching `grounded_in`, instead of rebuilding `title`/`tags`/`date` from DynamoDB. Verified live — hand-edited a real summary card's title directly in S3, ran `update_summary`, confirmed the hand-edit survived (previously would've been silently reverted), then restored the original.

First deploy crashed on `KeyError: 'SOURCES_TABLE'` before ever processing an event. `worker.py`'s own docstring had already named this exact tradeoff as the reason it avoids importing `clients.py` — the reconciler couldn't take that path since it genuinely needs `linkgen.py`, so it just accepts the fuller env var list instead.
  2. **Self-retrigger data loss.** `regenerate_note_links` rewrites a note's file to S3 as part of Stage 1's own delete-cleanup (and separately, from the agent's own `write_edge`/`update_summary`) — which re-triggers Stage 1's upsert handler on that same key. The first implementation used a full `put_item` there, which silently wiped `grounded_in` (a summary card's cluster membership) on that redundant re-trigger, since it's an attribute Stage 1 never sets itself. Caught directly in a live delete test against a real summary card with a real grounded member. Fixed by switching to a partial `update_item` (SET only the fields Stage 1 owns), making the self-retrigger idempotent instead of destructive, and added a regression test reproducing the exact scenario before redeploying.
- Live-verified after both fixes: a real hand-edit (tags changed, `created_at` correctly preserved — didn't jump to the top of Recent); a real rename (same `note_id`, new S3 key, confirmed one row not two); a real delete with both outgoing and incoming edges plus a summary card grounding the deleted note (all three cleanup directions confirmed — edges gone, source note's frontmatter regenerated, card's `grounded_in` correctly updated to `[]` not wiped entirely); a real missing-`note_id` note (hand-written, no frontmatter delimiters at all) correctly backfilled a `note_id`, rewrote the file, generated a sidecar, and was reachable via `GET /items/{note_id}` end to end. All test data cleaned up afterward (three-direction check applied to the test notes themselves, per `docs/schema-change-checklist.md`).

## Week 3 — Guardrail false positive, round 2: URL-based single-mode ingests (Aug 23, 2026)

- Surfaced during the `fetch_url` live verification above: a `single`-mode `/ingest` call with a `url` field (not `text`) was blocked outright — `finish_reason: "guardrail_intervened"` on the very first model turn, before `fetch_url` was ever called. This looked structurally like the `PROMPT_ATTACK` false positive already fixed earlier this week (`#11`, lowered `MEDIUM`), but that fix had only ever been verified against `text`-based ingests.
- Confirmed directly rather than guessed at: ran `aws bedrock-runtime apply-guardrail` against the exact blocked prompt text — `PROMPT_ATTACK` fired at `confidence: MEDIUM` against the deployed `MEDIUM`-strength filter (Bedrock blocks whenever confidence ≥ strength), so this was a second, genuinely distinct trigger of the same underlying pattern: `_build_prompt`'s `single`-mode instruction prefix ("Create exactly ONE atomic note from this source... do not create multiple notes even if...") followed immediately by "Ingest this URL: https://..." reads as an even closer structural match to indirect prompt injection than the `text`-based case — an imperative override immediately followed by "go fetch this."
- Fixed by rewording, not by loosening the guardrail further: iterated against `apply-guardrail` directly (no deploy needed per iteration) until a declarative "The user selected single-note mode for this ingestion. Summarize the source into one atomic note..." phrasing cleared the filter (`action: NONE`) for both the topic and no-topic `single`-mode variants, then applied the same wording to `app/api/routers/ingest.py`'s `_mode_instruction`. Preferred over raising `PROMPT_ATTACK` to `HIGH`, which would have quietly let through higher-confidence attack patterns too just to paper over this one false positive.
- Regression-covered in a new `app/api/tests/test_ingest_prompt.py` (pins the wording pattern that's known to clear the guardrail; can't exercise Bedrock's own classifier from a unit test, so that stayed a live/`apply-guardrail` check, matching this project's carve-out for LLM/classifier judgment). Deployed and re-verified live: both `single`-mode variants (with and without `topic`) now complete cleanly against the same URL that was previously blocked, each producing exactly one well-scoped note.

## Week 3 — Reconciler robustness: one neighbor's failure could orphan the deleted note's own row (Aug 23, 2026)

- Found while cleaning up the 34 test notes generated during the guardrail verification above (bulk `aws s3 rm` of interconnected notes, approved by the user first since it's a destructive/shared-state action): 10 of the 34 stayed stuck in DynamoDB after their S3 files were gone.
- Root cause, confirmed via CloudWatch traceback, not guessed: `_handle_delete`'s per-neighbor loop calls `regenerate_note_links(from_id)` unguarded for every note that had an incoming edge from the one being deleted. When a neighbor's *own* S3 file was also mid-deletion in the same batch, that call raised an unhandled `AccessDenied` (S3's standard response for `GetObject` on a now-missing key when the caller lacks `ListBucket` — a deliberate S3 behavior to avoid confirming non-existence, not an actual permissions bug) that propagated straight out of the handler, aborting it *before* it ever reached `items_table.delete_item` for the note the whole event was about. A best-effort step was able to block Stage 1's own unconditional correctness guarantee. Not just a test artifact — this can happen for real whenever several connected notes get removed together (`aws s3 sync --delete`, or fast manual deletes of related notes in Obsidian).
- Fixed by wrapping the per-neighbor block in `try`/`except`: a neighbor's frontmatter staying stale until the next edge write touches it is an acceptable best-effort miss; the deleted note's own row staying orphaned in DynamoDB is not — that's precisely the drift Stage 1 exists to prevent. Regression test added (`test_neighbor_regeneration_failure_does_not_block_own_deletion`) reproducing the exact race with a moto-mocked S3 delete of the neighbor's own object before calling `_handle_delete`.
- Deployed the fix, then finished cleaning up the 10 already-orphaned rows by invoking the deployed `slip-box-reconciler` Lambda directly with synthetic `ObjectRemoved` events for each remaining key (rather than hand-editing DynamoDB) — confirmed all 10 rows and their edges gone afterward, and spot-checked a real, non-test note that had an edge to one of the deleted test notes to confirm its frontmatter was correctly regenerated with no dangling reference.
