## Week 3 — FastAPI Backend Planning (Aug 21, 2026)

- Researched how to wire a FastAPI backend to the deployed AgentCore Runtime agent (invoking `bedrock-agentcore`'s `invoke_agent_runtime` via boto3, `runtimeSessionId` must be 33–256 chars — bare `uuid4()` at 32 chars is rejected, session IDs generated as `f"session-{uuid.uuid4()}"`).
- **Considered and rejected `agentcore add gateway`/BYO-agent as the API's front door.** AWS docs confirm AgentCore Gateway hard-restricts to GET/POST/DELETE only (no PATCH/PUT — blocks a plain edge-edit endpoint) and has no workable browser-auth story without standing up Cognito/OIDC. Confirmed this isn't a scoring risk either way — the hackathon rules state AgentCore usage strengthens Technical Implementation but "it's not required," and the agent itself is already correctly deployed on AgentCore Runtime regardless of what fronts the web API.
- **Confirmed API Gateway's Lambda-proxy integration has a hard, un-raisable ~29s timeout**, and `/ingest`'s multi-tool-call agent loop can realistically exceed it. Verified this is a real, AWS-documented limitation by reading AWS's own `aws-samples/sample-expose-agentcore-via-api-gateway` repo directly — their proxy Lambda timeout is set to exactly 30s to match, and their README names the limitation outright, pointing to AgentCore Gateway (not Function URLs) as their fix.
- **Decision: keep API Gateway exactly as originally scoped, make `/ingest` asynchronous instead.** A lightweight `ApiFunction` (FastAPI + Mangum) validates input and asynchronously invokes a second `WorkerFunction` (not fronted by API Gateway, so free of its timeout) that does the actual blocking `invoke_agent_runtime` call; the frontend polls `GET /items` for the result. Sidesteps the timeout entirely without deviating from AgentCore, without AgentCore Gateway's constraints, and without needing Lambda Function URLs or response streaming. REST API (not HTTP API) chosen specifically for native API Key + Usage Plan support, which satisfies review-todo #11's auth+rate-limiting requirement through infra config rather than hand-rolled app code.
- Full plan: two Lambda functions (`ApiFunction`, `WorkerFunction`) in a new `agentcore/cdk/lib/api-stack.ts` (same hand-rolled Foundation Stack pattern as `app-stack.ts`), new `app/api/` Python package (own `pyproject.toml`, Lambda-packaged via `uv pip install --target`, no Docker). Endpoints: async `POST /ingest`, `GET /items`, `GET /graph`, `PATCH`/`DELETE /edges/{from_id}/{edge_id}` (composite path — `slip-box-edges`' key schema is PK `from_id` + SK `edge_id`, no GSI for point-addressing by `edge_id` alone).
- Bedrock Guardrails deferred (would touch `MyAgent`'s model invocation, not this new stack; needs real threshold-tuning to be worth building) — plug-in point documented as `app/MyAgent/model/load.py`'s `load_model()`, for whenever `MyAgent` is next touched.

- Built the FastAPI backend per the plan: `agentcore/cdk/lib/api-stack.ts` (`ApiFunction` + `WorkerFunction`, REST API Gateway with native API Key + Usage Plan), `app/api/` package (`main.py`/`worker.py`/`routers/{ingest,items,graph,edges}.py`/`linkgen.py`/`models.py`/`clients.py`/`serialize.py`, `build.sh` for `uv`-based Lambda packaging targeting `aarch64-manylinux2014` to match ARM_64).
- Verified locally before any deploy: `tsc` compiles clean; `cdk synth` (via the real CLI at `node_modules/.bin/cdk` — `npx cdk` gets shadowed by this project's own `package.json` `bin.cdk` entry pointing at the app itself, worth remembering next time) produces exactly the expected resources — both Lambdas with correct handler/runtime/arch/timeout/env vars, precisely-scoped IAM policies (worker only gets `bedrock-agentcore:InvokeAgentRuntime`; the agent's own writes stay on the agent's IAM role), `ApiKeyRequired: true` on both proxy methods, usage plan throttle (5 rps/10 burst) and quota (2000/day) correctly attached to the stage.
- Verified the Python side against real AWS (not mocked): `POST /ingest` validation (422 on empty body, on both `text`+`url` together, on `research: true` → 501); `GET /items` and `GET /graph` return real data with `Decimal` confidence values correctly serialized as floats; `PATCH`/`DELETE /edges/{from_id}/{edge_id}` tested end-to-end on a throwaway edge — type/confidence update, history append, frontmatter regeneration on type change, and post-delete frontmatter cleanup all confirmed against the real S3 object.
- **Deployed** (`npm run deploy:api`) and found two real bugs the local/pre-deploy testing couldn't catch, both fixed and redeployed:
  - `WorkerFunction` crashed on cold start with `KeyError: 'S3_BUCKET'` — `worker.py` imported the shared `clients.py`, which unconditionally requires `S3_BUCKET`/`ITEMS_TABLE`/`EDGES_TABLE` at module load even though the worker never uses them (least-privilege design only gives it `AGENT_RUNTIME_ARN`). Fixed by giving `worker.py` its own minimal inline client setup instead of sharing the full module.
  - `bedrock-agentcore:InvokeAgentRuntime` 403'd against the deployed IAM policy even though the policy's `Resource` matched the runtime ARN exactly — the API actually operates on a `.../runtime-endpoint/DEFAULT` sub-resource (same pattern as an S3 bucket vs. its objects), so the policy needed `[agentRuntimeArn, \`${agentRuntimeArn}/*\`]`. This only surfaced once the Lambda's own narrowly-scoped role made the call — all earlier testing used broad local credentials that didn't exercise the resource-level restriction.
  - Both bugs found by actually invoking through the deployed stack (CloudWatch logs on `WorkerFunction`), not by code review — real infra behavior (env var propagation, IAM resource ARN shapes) that can't be verified any other way.
- Full round trip verified against the live deployed stack: `POST /ingest` → 202 with session ID (instant, confirming the async handoff isn't blocking) → agent completed in ~36s (comfortably past what API Gateway's 29s timeout would have allowed, validating the whole async design) → note + 3 correctly-typed edges (RELATED_TO/SUPPORTS/EXTENDS) visible via `/items` and `/graph` → `PATCH`/`DELETE` on a throwaway edge through the live API, frontmatter regenerated correctly on the real S3 object. Also confirmed the auth guardrail: 403 with no/wrong API key, 200 with the correct one.
- `review-todo.md` #11 marked RESOLVED — see there for detail.

- Fixed `update_summary`'s clobber bug (review-todo #9): it now reuses `write_edge`'s `_parse_frontmatter`/`_render_frontmatter` helpers to regenerate frontmatter from S3, only touching `grounded_in`, instead of rebuilding `title`/`tags`/`date` from DynamoDB. ## Week 3 — Reconciler robustness: one neighbor's failure could orphan the deleted note's own row (Aug 23, 2026)

- Found while cleaning up the 34 test notes generated during the guardrail verification above (bulk `aws s3 rm` of interconnected notes, approved by the user first since it's a destructive/shared-state action): 10 of the 34 stayed stuck in DynamoDB after their S3 files were gone.
- Root cause, confirmed via CloudWatch traceback, not guessed: `_handle_delete`'s per-neighbor loop calls `regenerate_note_links(from_id)` unguarded for every note that had an incoming edge from the one being deleted. When a neighbor's *own* S3 file was also mid-deletion in the same batch, that call raised an unhandled `AccessDenied` (S3's standard response for `GetObject` on a now-missing key when the caller lacks `ListBucket` — a deliberate S3 behavior to avoid confirming non-existence, not an actual permissions bug) that propagated straight out of the handler, aborting it *before* it ever reached `items_table.delete_item` for the note the whole event was about. A best-effort step was able to block Stage 1's own unconditional correctness guarantee. Not just a test artifact — this can happen for real whenever several connected notes get removed together (`aws s3 sync --delete`, or fast manual deletes of related notes in Obsidian).
- Fixed by wrapping the per-neighbor block in `try`/`except`: a neighbor's frontmatter staying stale until the next edge write touches it is an acceptable best-effort miss; the deleted note's own row staying orphaned in DynamoDB is not — that's precisely the drift Stage 1 exists to prevent. Regression test added (`test_neighbor_regeneration_failure_does_not_block_own_deletion`) reproducing the exact race with a moto-mocked S3 delete of the neighbor's own object before calling `_handle_delete`.
- Deployed the fix, then finished cleaning up the 10 already-orphaned rows by invoking the deployed `slip-box-reconciler` Lambda directly with synthetic `ObjectRemoved` events for each remaining key (rather than hand-editing DynamoDB) — confirmed all 10 rows and their edges gone afterward, and spot-checked a real, non-test note that had an edge to one of the deleted test notes to confirm its frontmatter was correctly regenerated with no dangling reference.

## Week 3 — Index Cards: sparse curated keyword entry points (Aug 23, 2026)

- Picked up next from `docs/frontend-ux-spec.md`'s own ritual table — "a keyword pointing at one or two entry notes, not an exhaustive list," Luhmann's second index alongside the numbered slips, distinct from tags (automatic, exhaustive) by being sparse and hand-picked.
- Opened with a real, unresolved tension from the user: "I don't like ordered by date... although maybe it'll still be useful to have newest in the list." Resolved by separating two genuinely different needs rather than picking one: recency belongs to the *desk* ("not quite yet putting the cards back in the slip case," the user's own framing) — the existing all-notes list keeps doing that job unchanged, just relabeled **Recent** to match; the Index itself is purely alphabetical by keyword, the filed/curated structure, full stop.
- Also requested mid-build: "index cards could and perhaps should lead to sub index cards." Luhmann's own index was flat — hierarchy emerged from *following links out of the entry note*, not a tree inside the index itself. Translated literally rather than building new nested-keyword machinery: on the note detail screen, any connection that's itself a curated entry point for some other keyword shows a small "↳ index: keyword" marker, sourced from data the connections view already fetches — no new hierarchy concept, no parent-keyword pointer.
- Data model: `index_keywords: list[str]`, a sparse attribute on `items` rows (absent, not `[]`, when nothing's curated) — the exact same shape as `tags` and the `reviewed_at` precedent above. Zero new-table cost: none of `docs/schema-change-checklist.md`'s 8 steps applied, confirmed directly against the checklist before building. New endpoints in `items.py`: `GET /index` (groups notes with any `index_keywords` by keyword, alphabetical — a full scan, but entries stay sparse by design so the matching-row count stays small regardless of corpus size, the same documented tradeoff `review-queue` already made), `POST`/`DELETE /items/{note_id}/index-keywords[/{keyword}]`.

## Week 3 — On-demand summarize: multi-select notes → one synthesized summary card (Aug 23, 2026)

- Testing Index Cards surfaced that the Summaries box was empty, which led to a real gap: `write_summary`/`update_summary` and the full "SUMMARY CARDS" system-prompt section already existed (built with the classification split) — including the exact line "If a user asks you to summarise their notes on a topic, search first, then write a summary card" — but there was no way to actually *ask*. `POST /ingest` only ever accepted a source to ingest.
- User's proposed interaction, more concrete than a freeform topic query and adopted as-is: multi-select several existing notes and tap "Summarize these," grounding the synthesis in an explicit, user-picked set — mirrors the selection-first pattern `CLAUDE.md` already describes for future `PermanentNote` writing ("the act of selecting and reading IS the thinking"), and needs no query parsing at all.
- Reused ingestion's entire async-invoke-and-poll mechanism rather than building a second one: `worker.py` already forwarded an optional `mode` field into the agent's invoke payload with nothing ever setting it (dead code, same shape as `write_edge`'s dedup fix above being a real bug waiting for the right trigger); the session-status table and its fields (`status`, `notes_created`, `skipped_reason`, `error`) were already fully generic, not ingest-specific; `hooks.py`'s `IngestOutcomeTracker` already tracked `write_summary` alongside `write_note`. ## Week 3 — Review gets Tag and Delete; note deletion becomes a reachable feature for the first time (Aug 23, 2026)

- Direct feedback: "the review should also be able to tag or delete." Tagging already existed in full (`note/[noteId].tsx`'s header icon → the Index Cards modal) — pure wiring into `review-stack.tsx`, nothing new to build. Deletion did not exist as a reachable feature anywhere in the app — confirmed by reading every router, the web app, and the Expo API client in full before starting.
- The hard part turned out to already be built and correct, just unreachable: `reconciler.py`'s `_handle_delete` (built for the Stage 1 reconciliation work) is a complete cascading cleanup — deletes outgoing edges, deletes incoming edges via `to_id-index`, scrubs the note out of any summary card's `grounded_in`, regenerates each affected neighbor's frontmatter — exactly the "three checks" discipline `docs/schema-change-checklist.md` documents from a real past incident (a dangling reference crashing the graph view's force-simulation). It's triggered purely by an S3 `ObjectRemoved` event; nothing had ever called it, because no `DELETE /items/{note_id}` route existed and the user-facing API Lambda held no `s3:DeleteObject` grant at all.
- New `DELETE /items/{note_id}` (`items.py`) deliberately does almost nothing itself: deletes the `.md` object (which triggers the reconciler) and its `.metadata.json` sidecar (best-effort, doesn't trigger anything, suffix-filtered out), and nothing else — it must *not* touch DynamoDB directly, since `_handle_delete` finds the item by scanning for its `s3_key` and needs the row to still exist when the event arrives; doing the DynamoDB delete from the API layer would silently skip all three cleanup checks, reintroducing the exact bug the checklist warns about. One new CDK grant (`s3:DeleteObject` added to the existing notes-bucket policy statement) — no DynamoDB grant changes needed at all.
- Bonus, free: this also closes the "known gap" flagged when Index Cards shipped (`index_keywords` cleanup on note deletion) — it's just an attribute on the item row, so once the reconciler deletes the row, there's nothing left to clean up.
- New test class locks in the design decision rather than just checking behavior: `test_row_is_not_deleted_here` asserts the DynamoDB row still exists immediately after the endpoint call, so a future edit that adds a premature `items_table.delete_item` fails a test instead of silently reintroducing the dangling-reference bug. 81/81 `app/api` tests pass.
- Mobile: `review-stack.tsx`'s single "Mark reviewed" button became a three-action row (Delete / Tag / Mark reviewed, `SymbolView` icons). Delete confirms first via a native destructive `Alert` (irreversible from the user's perspective, unlike marking reviewed) before calling the endpoint, then removes the note from the local stack optimistically — the real DynamoDB cleanup is asynchronous via the reconciler, nothing to poll for. Tag reuses the exact same `index-keyword.tsx` modal already built. Verified the route directly via `curl` (404 for a nonexistent note, correct auth) before handing back to device testing.
- Also fixed in the same round, from a device screenshot: list content in both the Slip Box and Review tabs was rendering flush against the floating tab bar, clipping the last row rather than trailing off with room to breathe — the tab bar floats over content instead of reserving its own space, and a `BottomTabInset` constant existed in `constants/theme.ts` for exactly this but had never actually been wired into any screen's `contentContainerStyle`. Fixed on both tabs; Review also gained its own pending-ingestion indicator (reusing the same tracker/component the Slip Box tab uses, extracted to `components/pending-row.tsx` to avoid a second copy) so a note or summary card mid-generation doesn't read as a false "you're caught up."

## Week 3 — Kindle share bug: a quote's own citation link was silently replacing the quote (Aug 24, 2026)

- Reported directly from a device screenshot: sharing a Kindle highlight showed "Link detected" with an `a.co` short link, not the quoted text at all.
- Root cause in `lib/shareIntent.ts`'s `toIngestPayload`: it checked `webUrl` first and returned unconditionally whenever present, before ever looking at `text`. Kindle's share sheet attaches *both* the quote and a link back to the book in the same share — the link unconditionally won, and the actual highlighted text was discarded outright. The agent would have ingested an Amazon product page instead of the user's own quote.
- Fixed by reversing the priority: real text content (anything that isn't itself just a bare URL) now wins, with `webUrl` attached as `source_url` — the exact citation mechanism already built for a client-fetched YouTube transcript — rather than being treated as a substitute for the content. A share that's genuinely just a link with no text (e.g. Safari with nothing selected) is unaffected; a link pasted as a Message's entire text still correctly becomes `{url}`, not `{text: "https://..."}`.
- `npx tsc --noEmit` clean; no JS test harness in this app, so this stays a live-verification fix per the standing carve-out for frontend behavior — confirmed by the user re-sharing the same Kindle highlight afterward.
